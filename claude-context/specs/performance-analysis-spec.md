# 图书馆预约系统性能测量与抢座失败分析

> **修订版本**: v2（基于审查反馈修订，修正了重试架构描述、补充了关键 bug 分析和遗漏项）

## 1. 目的

用户使用 QFNULibraryBook 自动抢座时，偶尔出现抢不到座位的情况。目标是：
- 系统性测量图书馆预约系统 API 的性能特征
- 深入分析预约机制的时间约束和竞争条件
- 定位抢座失败的根本原因（用户猜测与时间有关）
- 提出具体优化建议

## 2. 范围

**范围内：**
- 所有关键 API 端点的响应时间测量（只读端点，不触发预约）
- 预约时间窗口机制分析（"开放预约时间19:20" 约束）
- 脚本执行流程中的时间瓶颈识别
- 竞争条件和并发场景分析
- 网络延迟对成功率的影响
- **已确认的代码级 bug 对抢座成功率的影响**

**范围外：**
- 修改生产代码（仅提出建议，不自动修改）
- 破解或绕过系统安全机制
- 大量并发请求压测（避免触发风控）

## 3. 已确认的代码级问题（审查发现）

> 以下问题在规格审查中被确认为真实 bug，将作为分析的核心输入。

### 3.1 🔴 严重：`select_seat` 外层循环 `flag` 永远不为 `True`

**现象**：`select_seat` 函数中，`flag` 变量初始化为 `False`，但函数体内 **没有任何路径将其设为 `True`**。`post_to_get_seat` 调用 `check_reservation_status` 并获取返回值（`True` 表示已完成），但 `post_to_get_seat` **丢弃了该返回值**，不设置 `flag`。

**影响**：
- 每次选座（每个教室）**必定执行满 100 次外层迭代**，无论是否已预约成功
- 第一次成功后，后续 99 次迭代会收到 `"当前用户在该时段已存在座位预约，不可重复预约"`
- 每次迭代包含：`get_seat_info`（含 1s sleep）+ AES 加密 + POST 请求
- **单教室浪费时间 ≈ 100 秒**（100 次 × 1s sleep）
- 多教室场景下，第一个教室的 100 次迭代完成后才能进入第二个教室

**对抢座失败的影响**：这是最直接的效率瓶颈。在 19:20 黄金窗口期，浪费 100 秒意味着大量座位被其他用户抢走。

### 3.2 🟡 中等：重试架构效率问题

实际重试流程（非嵌套，而是顺序管道）：
```
select_seat 外层循环（100 次）:
  ├── get_seat_info → post_with_retry(max_retries=100, retry_delay=3s, timeout=120s)
  ├── 过滤空闲座位
  ├── post_to_get_seat → post_with_retry(max_retries=100, retry_delay=0s, timeout=120s)
  ├── check_reservation_status → 检查状态
  └── time.sleep(1)（在 get_seat_info 内部）
```

**关键特征**：
- `post_to_get_seat` 的 `retry_delay=0`：服务端返回非 200 时（如 429 限流），会以零延迟连续重试 100 次，可能触发服务端风控
- `get_seat_info` 的 `retry_delay=3`：如果座位查询本身失败，100 次重试需 ~300 秒
- `timeout=120` 过高：在 19:20 高峰期，单次请求若阻塞需等 2 分钟才超时
- 理论最坏情况：单教室 100 × (120s + 120s + 1s) = **24,100 秒 ≈ 6.7 小时**

### 3.3 🟡 中等：AES 密钥日期对齐问题

- AES 密钥基于 `datetime.now()` 实时生成（非脚本启动时缓存），跨午夜安全
- 但预约"明天"的座位时，密钥是"今天"的日期
- 需验证：服务端是否校验密钥日期与预约日期的一致性？如果不一致会导致静默失败

## 4. 技术方法

### 4.1 Phase 1 — API 性能探测（只读，不触发预约）

编写独立测量脚本 `py/performance_probe.py`，使用 `TokenManager` 进行认证：
- 第一步测量完整登录耗时（含 CAPTCHA），后续使用缓存 token
- 所有测量通过只读端点执行，不向 `/api/Seat/confirm` 发送探测性请求

| 测量项 | API 端点 | 目的 |
|--------|---------|------|
| 登录全链路耗时 | IDS CAS 完整流程 | 测量 token 获取总时间（含 CAPTCHA） |
| Token 缓存命中 | TokenManager.get_token() | 缓存 vs 重新登录的延迟差 |
| 时间段查询 | `/api/Seat/date` | segment 接口响应速度 |
| 座位列表查询 | `/api/Seat/seat` | 座位信息获取耗时 |
| 座位列表查询（无 sleep） | 自定义请求，跳过 sleep | 隔离 `time.sleep(1)` 的影响 |
| 用户状态查询 | `/api/Member/seat` | 作为到同一服务器的网络延迟代理 |
| AES 加密开销 | encrypt_seat_data() | 本地加密计算耗时 |
| 服务端错误码探测 | `/api/Member/seat`（观察响应码） | 记录 HTTP 状态码分布（200/429/500/503） |
| TCP 握手延迟 | curl connect-timeout | 底层网络往返时间 |

每个端点测量 10 次取平均值、P50、P95。

### 4.2 Phase 2 — 预约机制深度分析（代码 + 行为观察）

基于源码静态分析，结合 Phase 1 的实际数据，分析以下关键机制：

#### 4.2.1 时间窗口机制
- 系统在 19:20 开放次日预约（从 `"开放预约时间19:20"` 错误消息推断）
- **验证**：精确捕获服务端原始响应，确认该错误消息的完整内容和格式
- **验证**：`get_segment` 在 19:20 之前是否能获取到次日的时间段 ID（若不能，脚本无法预计算 segment）
- 分析脚本在 19:20 前后的行为差异

#### 4.2.2 执行流程时间线分析
绘制从脚本启动到预约成功的完整时间线：
```
T+0s     脚本启动
T+Xs     Token 获取完成
         └─ 首次登录: 含 IDS CAS + CAPTCHA (5~30s)
         └─ 缓存命中: ~0ms
T+X+As   获取日期 (本地计算, ~0ms)
T+X+A+Bs get_segment → POST /api/Seat/date
         └─ 正常: ~200ms
         └─ 19:20 前查询次日: 可能失败 → 阻塞
T+X+A+B+Cs get_seat_info → POST /api/Seat/seat
         └─ 正常: ~200ms + time.sleep(1) = ~1.2s
         └─ 服务端拥塞: 可能触发 120s 超时
T+X+A+B+C+Ds AES 加密 (~0.1ms, 可忽略)
T+X+A+B+C+D+Es post_to_get_seat → POST /api/Seat/confirm
         └─ 成功: ~200ms → 返回 "预约成功"
         └─ 未到时间: ~200ms → 返回 "开放预约时间19:20"
         └─ 被抢占: ~200ms → 返回 "该空间当前状态不可预约"
T+...    ⚠️ flag 未设为 True → 继续下一轮迭代（重复 B~E）
         总浪费: 99 次 × (~1.2s + ~0.4s) ≈ 158s
```

**关键瓶颈标注**：
1. 🔴 **flag bug 导致的 100 轮无效迭代**（最大瓶颈）
2. 🟡 **get_segment 在 19:20 前可能失败**（时间窗口硬约束）
3. 🟡 **120s HTTP timeout 过高**（高峰期单次阻塞可浪费 2 分钟）
4. 🟢 **login CAPTCHA 耗时**（如果 token 过期触发重新登录）

#### 4.2.3 错误状态映射表
验证 `check_reservation_status` 中所有状态码的准确性：

| 服务端 msg | 处理行为 | 是否正确 |
|-----------|---------|---------|
| `"预约成功"` | 检查座位 → 返回 True | ✅ |
| `"当前用户在该时段已存在座位预约，不可重复预约"` | 返回 True | ✅ 但外层不响应 |
| `"开放预约时间19:20"` | 返回 False → 继续重试 | ✅ |
| `"您尚未登录"` | 重新获取 token | ✅ |
| `"该空间当前状态不可预约"` | 返回 False → 继续重试 | ✅ |
| `"取消成功"` | sys.exit() | ⚠️ 仅在误触发时可见 |
| 其他未知消息 | 返回 True → **停止重试** | ⚠️ 需验证是否有遗漏的状态码 |

#### 4.2.4 竞争条件分析
- 模式 4（指定座位 228 号）：如果多人同时抢同一座位，查询到确认的时间差内被抢占
- "该空间当前状态不可预约" 后脚本重试，但 `flag` 不变 → 继续浪费迭代
- **多教室场景**：第一个教室 100 次迭代完成后才进入第二个 → 严重时间浪费

### 4.3 Phase 3 — 时间敏感性验证

**前置条件**：Token 在测试开始前 5 分钟预热（19:19:00），确保 1.5 小时有效期覆盖整个测试窗口。

1. **19:20 窗口测试**：
   - 19:19:50 启动脚本，记录到达 `/api/Seat/confirm` 的精确时间和响应
   - 验证 `get_segment` 在 19:19:50 是否能获取次日 segment（若不能则记录阻塞行为）
   - 记录服务端在 19:19:55 ~ 19:20:05 的响应时间变化

2. **延迟 vs 成功率**：在已知有空位的情况下，测试不同延迟（0ms、500ms、1s、2s、5s）下的预约成功率

3. **Token 预热测试**：对比"提前登录好 token" vs "19:20 才开始登录"的时间差

4. **CAPTCHA 重新登录测试**：模拟 token 过期场景，测量重新登录的完整耗时（含 CAPTCHA）

## 7. 风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 测量脚本触发真实预约 | 只使用只读端点（/api/Member/seat, /api/Seat/date），不向 /api/Seat/confirm 发送探测请求 |
| 频繁请求触发风控 | 请求间隔 ≥3s，总探测次数 ≤30 |
| 非预约时段无法测试时间敏感性 | 提供时间窗口测试脚本，用户可自行在 19:20 运行 |
| 网络波动影响测量 | 多次测量取中位数，记录异常值 |
| Token 在 19:20 窗口期过期 | 测试前 5 分钟预热 token（19:19:00），确保 1.5 小时有效期覆盖 |
| `post_to_get_seat` 的零延迟重试触发服务端限流 | 分析时记录该风险，优化建议中提出 retry_delay 配置化 |
| 零延迟 100 次重试形成事实上的 DDoS | 在风险评估中标注，建议加入退避策略 |
| CAPTCHA 重新登录耗时不可控 | 测量 CAPTCHA 成功率和平均耗时，纳入风险评估 |

## 8. 回滚策略

测量脚本为独立文件，不影响现有代码。如出现问题：
1. 删除 `py/performance_probe.py`
2. 测量数据文件（如有）一并清理
